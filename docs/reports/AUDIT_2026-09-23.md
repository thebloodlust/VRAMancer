## 4. Dettes et risques, par ordre d'importance

1. **Rien n'est publié.** 24 commits locaux, pas de tag, pas de PyPI, post non publié.
   Tout le travail de ces deux jours n'existe que sur ce disque — un disque qui meurt
   et tout disparaît. **C'est le risque n°1, et de loin.**
2. **Le récit de lancement ne correspond plus au matériel.** Le post et le tableau
   « Benchmarks » du README parlent d'une 3090 + 5070 Ti. La 5070 Ti n'est plus dans
   cette machine : ses chiffres ne sont plus reproductibles ici, et les 7 `[À REMPLIR]`
   du post ne peuvent pas être mesurés sans elle. Entre-temps, la paire 3090 + 7900 XT
   a produit le résultat le plus fort du projet (4.4×, agent validé, 64K tenus).
3. **Profil `coding` plafonné à 16K** (`VRM_N_CTX=16384`) alors que la paire tient 64K à
   69.6 tok/s. Un lecteur qui lit « 64K » dans un post et lance le profil obtiendra un
   refus au-delà de 16K. Soit le profil lit la VRAM disponible, soit la doc dit
   explicitement `VRM_N_CTX=65536`.
4. **Conflits de dépendances dans le venv** (D0.3) : Aider épingle
   `huggingface-hub==1.4.1`, `click==8.3.1`… ; `gptqmodel` veut numpy 2.2.6. Rien ne
   casse aujourd'hui, mais c'est une bombe à retardement pour quiconque clone le dépôt.
   Solution connue : `pipx install aider-chat`.
5. **Code sans consommateur** : les 3 modules de `core/orchestrator/` (documentés
   honnêtement), 6 k lignes dans `experimental/`, 5.5 k dans `_deprecated/`. Ce n'est pas
   dangereux, mais c'est ~25 % de la surface Python que personne n'exécute en production.
6. `count_tokens()` retombe toujours sur un compte de mots pour les backends sans
   tokenizer (Ollama notamment). Corrigé pour llama-server, pas généralisé.

## 5. Conseils, dans l'ordre

1. **Pousser maintenant** (`git push`), avant toute autre chose. Coût : 10 secondes.
2. **Révoquer le token GitHub** si ce n'est pas fait, puis en créer un neuf pour le push.
3. **Décider du récit de lancement** — c'est cette décision qui tranche le sort de la
   7900 XT (voir §6). Recommandation : **basculer sur la paire 3090 + 7900 XT**. C'est
   plus fort (cross-vendor, 4.4×, un Q6_K qui ne tient sur aucune carte), c'est
   mesuré aujourd'hui, et c'est différenciant : presque personne ne publie de chiffres
   NVIDIA + AMD ensemble.
4. Corriger le plafond 16K du profil `coding` avant de citer 32K/64K.
5. PyPI + tag + post (D1), dans cet ordre, en exécutant littéralement le bloc Setup du
   post dans un venv vierge avant de publier.
6. Seulement ensuite : `pipx` pour Aider, ménage d'`experimental/`.

## 6. La RX 7900 XT : garder ou vendre ?

**Techniquement, il ne reste rien à tester.** Stabilité (seule et en paire), support
AMD, cross-vendor dans ses trois régimes, reproduction, agent réel, contexte long :
tout est mesuré et consigné. Les bugs qu'elle a révélés sont corrigés dans le code et
ne dépendent plus d'elle.

**La vraie question n'est pas technique, elle est éditoriale :**

- **Lancement sur la paire 3090 + 7900 XT** (recommandé) → **garde-la** jusqu'à la
  publication et quelques semaines après : il faut pouvoir reproduire les chiffres,
  répondre aux questions des lecteurs, refaire une mesure contestée. La vendre juste
  avant de publier des chiffres obtenus avec elle, c'est publier ce qu'on ne peut plus
  vérifier.
- **Lancement sur 3090 + 5070 Ti** (le post actuel) → elle ne sert plus à rien pour le
  lancement, **tu peux la vendre** — mais il faut alors récupérer la 5070 Ti pour
  remplir les 7 chiffres manquants.
- **Usage personnel** : si tes modèles tiennent dans 24 GB, elle te coûte 32 % de
  débit ; si tu veux du Q6/Q8 sur un 30B ou des contextes de 64K, elle te les donne.

## 7. Que penser des résultats en GPU mixte ?

Trois choses, dans l'ordre d'importance :

1. **Ça marche, sans rien faire.** llama.cpp Vulkan met une NVIDIA et une AMD dans le
   même calcul, sans ROCm, sans configuration, avec une variance de ±3 %. C'est la vraie
   surprise de la session : on s'attendait à devoir écrire un pont maison, il n'en faut
   aucun.
2. **Ça ne paie que dans une fenêtre précise**, et cette fenêtre est tout le propos de
   VRAMancer : quand le modèle ne tient QUE dans la VRAM cumulée. Hors de cette fenêtre,
   c'est −32 % (modèle qui tient sur une carte) ou un gain qui ne sert à rien (modèle
   qui dépasse tout). La règle est simple et tient en une ligne de README : *ajoute une
   carte, même d'une autre marque, si elle fait passer ton modèle sous le plafond de VRAM
   cumulée.*
3. **La valeur de VRAMancer est dans l'orchestration, pas dans le transport.** Le
   transport est résolu par llama.cpp. Ce qui manquait — et que VRAMancer faisait
   *mal* jusqu'à hier — c'est de voir la deuxième carte, de choisir le bon backend, de
   répartir la VRAM, de ne pas charger en CPU par erreur. Trois bugs sur dix de la
   session étaient exactement ça, et chacun coûtait entre 4× et 19× de débit en silence.
   C'est le meilleur argument du projet : **sans orchestration correcte, le matériel
   est là et on laisse 4.4× sur la table sans le savoir.**

Une limite à garder en tête : tout ceci est mesuré sur **une** paire, dans **une** VM, avec
**un** modèle MoE (Qwen3.6-35B-A3B, 3 B paramètres actifs par token). Sur un modèle dense
de taille comparable, tous les débits seraient bien plus bas (≈10× plus de calcul par
token), et le rapport paire / carte seule n'est **pas mesuré** — il pourrait être plus
faible comme plus fort (le débordement CPU d'une carte seule coûte beaucoup plus cher en
dense). À dire tel quel dans le post : « mesuré sur un MoE ».
