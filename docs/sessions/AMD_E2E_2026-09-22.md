# VRAMancer de bout en bout sur RX 7900 XT (sans NVIDIA, sans ROCm)

> Mesuré le 2026-09-22. Machine : VM QEMU, RX 7900 XT en passthrough VFIO, **aucune
> carte NVIDIA utilisable** (module noyau absent), **ROCm non installé**. Tout passe
> par Vulkan/RADV. Chiffres bruts, copiés des sorties.

## Ce qui a été lancé

`vramancer serve --model Qwen3.6-35B-A3B-UD-Q4_K_M.gguf --port 5030 --gpus 1`
(`VRM_N_CTX=8192`, `VRM_LLAMA_NGL=38`), puis des clients HTTP standards.

## Résultat principal : 2.0 → 31.8 tok/s

| Chemin | Débit | VRAM utilisée | GPU |
|---|---|---|---|
| `vramancer serve` **avant correctif** | **2.00 tok/s** | 335 MiB | 1 % — la carte ne fait rien |
| `vramancer serve` **après correctif** | **31.8 – 33.0 tok/s** | 19 961 MiB | 52 % |
| `llama-bench` direct (référence) | 37.78 tok/s | 19.8 GiB | — |

Cause : `llama-cpp-python` est compilé pour **un** accélérateur. La roue installée est
une roue CUDA ; elle s'importe parfaitement sur une machine AMD mais
`llama_supports_gpu_offload()` renvoie False, et le modèle est alors chargé
**entièrement en CPU, sans un mot**. Le correctif détecte ce cas et bascule sur le
sous-processus `llama-server` (build Vulkan téléchargé automatiquement).

L'écart restant entre 31.8 et 37.78 tok/s est le coût HTTP + prompt sur une requête
de 128 tokens, pas une perte GPU.

## Tool calling — validé de bout en bout

`examples/tool_calling_quickstart.py` (client `openai` officiel) contre ce serveur :

```
→ tool_call : get_weather({'city': 'Toulouse'})
→ résultat  : {'city': 'Toulouse', 'temp_c': 18, 'conditions': 'nuageux'}

Réponse finale :
Il fait 18°C et il est nuageux à Toulouse.
```

Le modèle émet du `<tool_call>` Hermes, VRAMancer le convertit au format OpenAI, le
client exécute l'outil, renvoie le résultat, le modèle rédige la réponse finale. **Le
chemin agent complet fonctionne sur AMD.**

## Concurrence

| Requêtes simultanées | Durée totale | Latence min/max | Débit agrégé |
|---|---|---|---|
| 1 | 2.0 s | 2.0 / 2.0 s | 31.5 tok/s |
| 4 | 4.0 s | 1.8 / 4.0 s | **64.5 tok/s** |
| 8 | 8.8 s | 3.6 / 8.8 s | 58.5 tok/s |

Le parallélisme double le débit agrégé à 4 requêtes, puis plafonne : à 8, on ne gagne
plus rien et la latence individuelle se dégrade proportionnellement. Sur cette carte et
ce modèle, **4 requêtes simultanées est le bon point de fonctionnement**.

## Deux autres bugs trouvés en faisant tourner ça

1. **Un client envoyant un nom de modèle arbitraire mettait le serveur à terre.**
   `{"model": "local"}` — ce qu'envoient beaucoup de clients OpenAI — partait en
   résolution HuggingFace. Or `PipelineRegistry.load()` **arrête le pipeline courant
   AVANT** de charger le nouveau : le chargement échouait et le serveur se retrouvait
   **sans aucun modèle**, répondant 500 à tout le monde. Une seule requête mal formée
   suffisait. Corrigé : un nom qui ne ressemble pas à une référence de modèle
   (pas de `/`, pas de `.gguf`, pas un chemin existant) est ignoré et le modèle chargé
   est servi — le comportement de llama.cpp et LM Studio. 3 tests de non-régression.

2. **Le sous-processus `llama-server` survivait à son parent** : ~20 GB de VRAM et le
   port 8081 restaient squattés, et le démarrage suivant échouait de façon
   incompréhensible (« Address already in use », puis modèle non chargé — ça m'a coûté
   trois faux diagnostics dans cette session). Corrigé par un `weakref.finalize` +
   `atexit`, plus une recherche de port libre si un orphelin traîne encore.

## Ce que ça ne dit pas

- Rien sur la paire NVIDIA + AMD (question D3.d) — la 3090 n'a pas de module noyau.
- Rien sur ROCm/torch-hip : non installé, non nécessaire pour ce qui précède.
- Aider n'a pas été rejoué dans cette session ; c'est `examples/tool_calling_quickstart.py`
  qui valide le round-trip d'outils ici.
